# ADR-010 — Model router: policy, capability matrix, validated fallback, confidence

**Status:** accepted · **Date:** 2026-09-06 · **Phase:** 7

## Context

The specification (§55–§57, §34, §36) wants a router that decides per call which model serves a task, keeps Protea out of tasks it has not proven it can do, respects tenant privacy and cost policies, falls back when an answer does not validate, reports a confidence that is not the model's opinion of itself, and records every decision and fallback. aria's own routing today is a lane classifier and a per-partner model choice; nothing there knows about benchmark evidence or validation outcomes. The router has to work before any Protea model exists (every call goes to a frontier route) and hand traffic to Protea in controlled steps once ZaraBench reports say a category is ready.

## Decisions

1. **The policy is data, not code.** `configs/routing/*.yaml` (kind `routing`, validated like every other config) lists the candidates (route name, provider, model, self-hosted flag, cost and quality tiers, complexity ceiling, task types, whether a benchmark score is required, a pinned version label), the default route, the fallback order, per-category thresholds, the canary share, the confidence floor and the attempt limit. The router never invents a candidate and the default route may never be benchmark-gated, so a fresh deployment always has somewhere to send traffic.
2. **Benchmark evidence gates Protea.** A candidate with `requires_benchmark` serves a task type only when the capability matrix holds a non-partial ZaraBench report for that provider and model whose score in the task's category meets the threshold. The matrix is read from committed reports under `reports_dir`; mock and reference runs are never evidence. No report means the route is ineligible whatever the policy says.
3. **Canary by tenant, not by request.** A stable SHA-256 bucket of the hashed tenant reference decides whether a tenant is inside `canary_percent`; a tenant is therefore either always or never on a benchmark-gated route for a given policy version, which keeps behaviour explainable per customer and makes rollback a one-line change (canary 0).
4. **Hard constraints before preference.** `privacy: strict` removes every route that is not self-hosted; if none remains the router refuses (`NoRouteError`, HTTP 409) rather than sending data to a third party. Declared task types and complexity ceilings drop candidates next. Only the survivors are ordered by the cost policy: `cheapest`, `best`, or `balanced` (benchmark-proven self-hosted routes first, then the operator's declared order, then quality).
5. **Task type and complexity come from the request shape.** Explicit `task_type` metadata wins; otherwise tools, schema and a small phrase list classify the call, and a rule-based score over prompt length, tool and connector counts and financial signals sets `low | medium | high`. No model call is spent on routing.
6. **Fallback is validated.** Execution tries the chosen route, then the fallback chain, up to `max_attempts`. With a schema the validation gate (ADR-009) runs on each attempt; a still-invalid answer, a provider error, a bad finish reason (`length`, `refusal`, `error`) or a confidence below `min_confidence` moves to the next route. Fallback attempts carry `metadata.fallback = true`, which the provider layer copies onto the usage event.
7. **Confidence is computed from evidence.** Signals: schema validity and repair count from the gate, whether emitted tool calls name declared tools, the serving model's benchmark score for the category, and the route's recent success rate for the task type (sliding window). The score is the weighted mean of the signals that apply. Nothing asks the model how sure it is.
8. **Every decision is an event.** `RouteEvent` records identifiers and outcomes only — task type, complexity, privacy, canary and pin flags, chosen and served routes, the served model, each `FallbackEvent` (from, to, reason, attempt), confidence, gate validity, latency and tokens — never prompt or completion text. Sinks: application log (default), in-memory (tests) or append-only JSONL (`serve.route_events`) for the Phase 9 dashboards.
9. **Per-agent pinning.** A request may name a `pinned_route`; it is honoured when that route passes the hard constraints and benchmark gate, and otherwise rejected with the reason recorded on the decision, so a pinned agent never silently drifts to another model but also never bypasses privacy or evidence.

## Consequences

- The facade gains `/v1/route/generate` and `/v1/route/structured` (mounted only when `serve.routing_policy` is set). The response returns the decision, fallbacks and confidence alongside the answer; 422 when no route produced an acceptable answer, 502 when every route failed, 409 when policy forbids all routes. `protea route explain` shows the same decision offline and `protea route matrix` prints the evidence.
- The committed policy ships with `canary_percent: 0` and thresholds of 0.75–0.85 by category. Moving Protea into production is a policy change reviewed in a PR, preceded by a committed ZaraBench report; that is the release gate of ADR-007 applied per category.
- Frontier providers are still built from environment credentials; in tests candidates are injected directly. Nothing here spends tokens by itself.
- aria's Phase 6 compiler backend selection (`ZARA_COMPILER_BACKEND`) is the consumer: once the facade runs with a routing policy, the compiler can post to `/v1/route/structured` and let the policy choose, instead of choosing a backend at process start. That wiring lands with Phase 8/9 once the facade is deployed.
